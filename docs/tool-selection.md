# Tool selection for the design workspace

Source review recorded at 2026-10-03T00:03:32Z. Scope: [implementation scope](implementation-scope.md).

The application uses React and React Flow for the editable design surface. A separate project model connects needs, rules, components and evaluation evidence. This separation lets the same project support a director's outcome review and an engineer's implementation handoff.

## What each layer means

| Layer         | Selected approach                                           | Responsibility                                                                        |
| ------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Discovery     | DDD and EventStorming-informed questions                    | Identify actors, events, tacit rules, exceptions and disagreements.                   |
| Project model | Versioned JSON with validated identifiers and relationships | Preserve meaning, ownership, source references and unresolved decisions across views. |
| Architecture  | C4-informed levels                                          | Describe system boundaries and internal components at an appropriate level of detail. |
| Rules         | Explicit decision tables                                    | Make conditions and outcomes reviewable through examples.                             |
| Behavior      | Statechart-informed states and transitions                  | Explain approval, cancellation, retries and partial completion.                       |
| Canvas        | React Flow                                                  | Display and edit nodes and relationships with keyboard alternatives.                  |
| Evidence      | Linked cases, datasets, criteria and review records         | Show what supports a decision and what still needs investigation.                     |

C4 is independent of notation and tooling. It supports system context, container and component views. EventStorming is a collaborative discovery method. Neither supplies a complete executable specification. The discovery questions use incremental notation so participants can start with a concrete task. [C4](https://c4model.com/), [EventStorming](https://www.eventstorming.com/), [incremental notation](https://www.eventstorming.com/patterns/incremental-notation/)

A diagram in this workspace does not claim BPMN, DMN or statechart conformance. Those formats have defined semantics. A future adapter must name its supported version and preserve unsupported content without silently translating it into a different meaning. [BPMN specification](https://www.omg.org/spec/BPMN/2.0.2/), [DMN specifications](https://www.omg.org/spec/DMN/)

## Public website and local companion

GitHub Pages hosts the static React build. Project state remains in the browser until the user exports it. The public site has no model credentials or server-side agent runtime. Role selection changes the guidance; it does not authenticate a person or grant approval authority.

The planned local Claude Code companion is a separate boundary. A person chooses the specification to submit through their existing local login. The companion requests schema-constrained project data with tools, MCP and project customizations disabled. It validates the result before the browser imports the file. It does not implement or deploy the proposed design. The implementation scope defines the acceptance checks for that boundary.

Project imports remain inert data. A parser validates the supported format, identifiers and relationships before replacement. A preview must expose unsupported material and changes to existing work. Text that claims approval remains an imported claim until a person reviews it. Scripts, plugins and remote includes are not part of this design-file contract.

## Collaboration and agent handoff

Every role contributes to the same project revision. Pair guidance provides a focused question and an artifact to review together. It supports a workshop or an asynchronous handoff. Concurrent edits and identity-backed approvals need an additional service; role cards do not provide those capabilities.

An implementation handoff includes the authorized scope, source authority, business rules, component contracts and acceptance examples. It also carries evaluation criteria, operating constraints and unresolved decisions. The receiving agent can propose a bounded implementation and return evidence. It cannot treat a complete form, a generated diagram or its own assessment as release approval.

The project model preserves the relationship between a need, its rule, the implementation component and the evidence used to judge it. Specialized editors and runtime products can attach to that model when a project needs their semantics. Their adoption does not remove the need for a named decision owner.
