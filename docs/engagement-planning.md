# Engagement planning

Glen directly requested a generic professional-services workspace for engineering-background project managers and technical leads. This revision implements issue #2. Spec review is waived in the active conversation. It does not claim conformity with a project-management standard.

## Intent

Start with the client's mandate, user and business impact, working relationship and delivery constraints. Offer nine core checkpoints across discovery/design, delivery, transition and operation. Keep architecture, model evaluation and sector-specific routing as optional specialist work. A person can hold several responsibilities. Phases can be revisited or skipped; an advisory engagement need not deliver software.

## Acceptance

- The guide presents a generic client-service improvement narrative and links directly to engagement checkpoints. The full AI support example is explicitly optional.
- Core checkpoints produce a mandate, responsibility agreement, risk record, phase plan, design/evidence plan, change record, acceptance/handover record, operating plan and benefits/closure review. Each explains when to use it.
- Specialist templates remain available through an explicit picker. All twelve legacy IDs, question IDs and meanings remain unchanged.
- Every saved decision remains visible and editable regardless of the template picker. Unknown template IDs and old answer keys remain visible, editable and exported.
- PM and engineer guidance includes client relationships, commercial constraints, technical design, evidence and operations. Roles represent responsibilities, not separate required hires.
- Source division/product fields are optional unless routing is selected. Generic engagements do not require a model or held-out dataset.
- Existing schema v1, tutorial IDs/order, lifecycle values and storage keys remain unchanged. No automatic migration, inferred dates, generated estimates or approval claims.
- Unit and mobile/desktop browser checks prove persistence, export, legacy records, optional topics and generic source validation. Existing import, architecture and specialist workflows remain functional.

## Boundaries

This is a planning and evidence workspace, not a scheduling engine, live collaboration service or production monitoring system. Existing architecture and evaluation views describe an optional software design; their gaps are not an engagement completion score. The offline specification converter prompt preserves advisory scopes without inventing software. Its provider access boundary is unchanged; validation uses an injected runner, not a model call. No backend, model calls, deployment or automated approvals are added. The optional AI example retains its existing data and routing semantics.

New blank projects have no software graph or generated checks. Explicit architecture suggestions and the optional AI example retain their existing behaviour. Component-link gaps apply only when a graph is recorded; general need acceptance and evidence requirements remain. Evaluation labels accept ordinary review material and criteria.
